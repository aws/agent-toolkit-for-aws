# IAM and resource creation reference

All angle-bracket values are placeholders. Build JSON files with validated values, not shell interpolation of service prose. Get explicit approval for each write. These are templates, not executable helpers, except the external-ID generator under New role.

## Minimum source-role permissions

- `s3:ListBucket` on `arn:aws:s3:::<bucket>`; include the code and context prefixes if a condition limits listing, and account for the integration's HeadBucket check.
- `s3:GetObject` and `s3:GetObjectVersion` on `arn:aws:s3:::<bucket>/<code-prefix>*` and `arn:aws:s3:::<bucket>/<context-prefix>*`.
- `s3:PutObject`, `s3:GetObject` and `s3:GetObjectVersion` on `arn:aws:s3:::<bucket>/continuum-patches/*` for patch delivery and reconciliation. Keep these together in the `DeliverContinuumPatches` statement described by the public getting-started guide.
- `kms:Decrypt` on the exact customer-managed KMS key ARN if source is SSE-KMS. Resolve an alias with `aws kms describe-key`; an alias ARN is not a decrypt resource. A key policy must also allow access. Do not add KMS permissions for SSE-S3.

For existing roles, evaluate every statement including Deny, NotAction, NotResource, conditions, and boundaries. If the result is ambiguous, report unknown. Do not grant redundant wildcard access to work around uncertainty. Permission gaps can ONLY be added using `aws iam put-role-policy --role-name <role-name> --policy-name <new-unused-name> --policy-document file://<gap-policy.json>`, after listing existing names and obtaining approval. Never overwrite a name, attach a policy, create a managed policy version, or edit an existing policy.

## New role

The public [AWS Continuum getting-started guide](https://docs.aws.amazon.com/continuum/latest/userguide/cv-getting-started.html#cv-getting-started-s3-role) requires a same-account source role under `/continuum/integrations/` that trusts the AWS service principal `continuum.amazonaws.com`, with a caller-provided external ID. Generate the external ID and trust policy with this skill's checked-in script, never by composing an ID yourself from names, dates, or other guessable text:

```bash
node <skill-directory>/scripts/new-external-id.mjs <trust.json>
```

Resolve `<skill-directory>` from this skill's actual installed path. The script prints a 256-bit random external ID (64 hex characters) and writes `<trust.json>` owner-only, refusing an existing path; choose a new path rather than deleting anything. Show the printed ID to the developer as part of the exact plan and use that same value in the `create-integration` request. The written trust policy has this shape:

```json
{"Version":"2012-10-17","Statement":[{"Sid":"ContinuumSourceAccess","Effect":"Allow","Principal":{"Service":"continuum.amazonaws.com"},"Action":"sts:AssumeRole","Condition":{"StringEquals":{"sts:ExternalId":"<generated-external-id>"}}}]}
```

Do not use the caller account root, an AWS account principal, or a guessed principal ARN. The public CLI model describes `externalId` as caller-provided and required by the role trust policy; it is not returned or generated by `create-integration`. After consent: `aws iam create-role --path /continuum/integrations/ --role-name <new-name> --assume-role-policy-document file://<trust.json>`. Add the required permissions as a new inline policy. Never modify existing trust; choose a different role if it does not fit. Keep external IDs out of reports; they are integration configuration, not findings.

The caller creating an integration also needs `iam:PassRole` on that exact role, restricted with `iam:PassedToService` equal to `continuum.amazonaws.com`. Explain a missing caller grant; do not mutate caller IAM implicitly.

## S3 scanner-support preflight

Before any source upload or environment write, count every repository selected for the environment across all integrations. For S3, inventory the planned repository ZIPs and existing direct-child ZIPs at the intended prefix; upload records under `.continuum/uploads/` do not count. Add repository selections from GitHub or any other integration. Then calculate and show the per-integration counts and their total yourself. Exactly 10 passes the documented default; 11 or more fails unless the developer says AWS granted a higher limit. No quota script is needed.

The public [AWS Continuum quotas page](https://docs.aws.amazon.com/continuum/latest/userguide/quotas.html) documents **10 repositories per environment across all integrations**. Exactly 10 passes. More than 10 stops setup before any write. Report the actual count, limit, and citation, and offer: choose 10 or fewer repositories; split them into separate, logically grouped environments with 10 or fewer each; or ask the AWS account team for a quota increase. Never silently omit packages or combine repositories to evade the count. Use a higher limit only when the developer says it was granted, and record their statement together with the account, Region, count, effective limit, and provenance in the approved plan.

Separately measure every repository ZIP's exact byte size and the largest archive, and verify the bucket account and Region against the selected Continuum account and Region. The current quotas page and public getting-started guide state no per-ZIP byte-size limit, so report the measured largest ZIP and label that limit **not publicly documented**; only ZIP-size support retains the unknown-limit warning. The installed CLI input model caps `s3Sources` at one per environment. A successful upload, integration creation, or environment creation does not prove scanner support.

## New bucket

Prefer an existing bucket owned by the caller in the chosen region. If the user approves a new one, show bucket name, region, encryption, public-access-block, and lifecycle settings independently. Create it with `--object-ownership BucketOwnerEnforced` to disable ACLs; in regions other than us-east-1 also include `--create-bucket-configuration LocationConstraint=<region>`. Treat BucketAlreadyExists as fatal. Immediately verify with guarded head-bucket, then use `--expected-bucket-owner <caller-account>` for every subsequent bucket request, including encryption and public access block writes. Do not reapply settings to reused buckets. Never delete a bucket.

## New integration

`aws continuum create-integration --name <name> --provider-configuration file://<provider.json>`:

```json
{"s3":{"bucket":"<bucket>","roleArn":"<role-arn>","externalId":"<same-external-id-as-trust>"}}
```

The service assumes this role and checks bucket access. Read the returned integrationId and get-integration; tolerate IAM propagation only by a bounded retry of the same approved request. Never create duplicates on ambiguous responses: list first.

## New environment

Publish the full first code version before creation using [the reporting skill's packaging contract](../../reporting-continuum-security/references/packaging.md); show that upload as part of the plan. Include the plain step **Write a small upload record so an interrupted upload is never mistaken for a complete one.** The one record for version N lives at `<codePrefix>.continuum/uploads/v<N>.json`, starts as `uploading` through conditional create, and changes to `complete` through an ETag-guarded update only after zip verification. `aws continuum create-environment --name <name> --configuration file://<configuration.json>`:

```json
{"codeConfiguration":{"sourceConfiguration":{"s3Sources":[{"integrationId":"<integration-id>","codePrefix":"code/<repository-name>/","contextPrefix":"context/<repository-name>/"}]},"environmentConfiguration":{"patchCreationPolicy":"ENABLED","scanFrequency":"<approved-ISO-8601-duration>"}}}
```

Prefixes must be nonempty folders outside `continuum-patches/`, never a zip object. The public API documents scan frequency as: **“P1D, P2D, or P7D. PT0H disables recurring scans. Defaults to P1D.”** Ask the developer to choose one of those four values before preparing the environment request. Present `PT0H` as **no recurring scans**, not as no initial scan: creation still starts initial scanning automatically. Never accept an omitted cadence as consent to the `P1D` default. Reuse never implies update-environment. Changes require a new explicit plan.
