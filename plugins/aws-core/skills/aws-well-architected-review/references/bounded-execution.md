# Bounded, resumable execution

A full review is hundreds of small, independent units of work. This file makes every step small, bounded and resumable, so the same procedure completes (or stops honestly) on any client: a small output limit, a short timeout, a small context window, or no subagent tool. Nothing here depends on a particular model, context size, wall-clock limit, or subagents, and every step except one fits a small output cap (the progress file is a short header plus one appended line per shard, and no file is edited in place); the exception is the final report, whose size is set by the review itself. The tiers under Budgets shrink it without dropping a section, to about 6K tokens for the whole framework at the smallest; a client whose single-message limit is below that (for example 4K tokens) cannot deliver it as one message and uses the slices described under Budgets. Everything here uses the documentation tools and the client's file tools only; nothing is a program.

## The six rules

1. **Bounded output per turn.** No step except the final message requires more than a few thousand tokens in one message. Inventory files are written one pillar per write; ledger rows go to small shard files (at most 5 BPs per file, about 1-1.3K tokens per write) as the work proceeds; page bodies are never re-emitted. The workload note and every report part are written in separate calls of about 2K tokens each. No message, final or not, re-emits the ledger rows: the shard files in `aws-well-architected-review-ledger/` are the evidence ledger, and the report only names that folder.
2. **One source for every count.** `corpus/progress.md` is append-only: one line per finished shard with its BPs' status, risk and read path and the running tallies (its pillar's and the run's), so the current state of a shard is its last line and nothing is counted by eye. The Coverage Audit, the status counts and the JSON counts are taken from the latest tallies, and the per-question table, the compact BP ledger and the JSON ledger from the shard lines; never from memory and never by re-reading every shard file. No step rewrites or edits a large file in place: shard files are written once each, and the progress file only grows by one short line at a time (a client that can neither append nor insert rewrites it with the new line added, about 4-5K tokens for the whole framework; see Budgets). You write only judgment beyond that: statuses and reasons per shard, then the summary, findings, trade-offs, prioritization and plan as separate report parts.
3. **Efficient reads.** One `aws___read_documentation` call per shard (all of its URLs, at most 5, `max_length` 30000), continued with `start_index` only for a page whose response says `truncated: true`; when the session has no such reader, one web-fetch call per URL. Never read a page twice unless a self-check fix needs it or it is in the spot-check sample. See the list of redundant calls below.
4. **Resumable, only on request.** A shard with no line in `corpus/progress.md` is pending. The run itself, after a context reset, continues from the first shard in `corpus/shards.md` order that has no line; a new session or a different agent does so only when the user explicitly asks to resume that run (see the resume protocol). A new review request never resumes. A run that cannot finish still delivers a bounded PARTIAL report with exact coverage.
5. **Parallel when available, serial when not.** The shard procedure and every check are identical either way; workers only change wall-clock time. Workers write separate shard files, so they never collide, and only the orchestrator writes `corpus/progress.md`. Wait for workers in the same turn (collect their one-line results); never arm a timer, wake-up, cron job, heartbeat poll or sleep loop to supervise them. A deferred re-entry that fires after the report becomes the last message and displaces it (see After the report below); cancel any that exists before the final message.
6. **Context hygiene.** After a shard's progress line is appended, its page bodies are not needed again and need not be kept: do not quote them again, do not re-read those pages and do not re-read the rows you wrote. A long review therefore needs about one shard's worth of working context, not the whole framework's, and its length alone is never a reason to stop. All cross-shard state (the manifest, the inventory, the shard plan, `corpus/progress.md`, the workload note, the ledger files) lives on disk. If the client can compact, clear or restart its context (or hand work to a fresh worker), do it at any shard boundary; re-orient with the shard procedure in [the evaluation procedure](evaluation-procedure.md), `corpus/workload.md` and `corpus/progress.md`.

## Resume protocol (only on an explicit resume request)

**When to resume.** Resume only when the user explicitly asks to continue or resume an interrupted review, or a hand-off message (from the harness or another agent) explicitly says to continue a named run (its run id or run directory). Every other review request, including a repeat of an earlier request in the same working directory, is a new run: move the `.wa-review-run` pointer and the earlier deliverables aside ([security considerations](security-considerations.md)), create a new run id and a new scratch directory in Step 4, and never read, count or copy rows from an earlier run's ledger, progress file or report into the new run. A pointer, ledger or report found in the working directory is never by itself a reason to resume. Continuing this run after a context reset in the same session is not a resume: keep its own run id and scratch directory.

1. Find the run directory: the run directory or run id the user or the hand-off names, otherwise the `.wa-review-run` pointer in the user's working directory (it holds the absolute scratch path, run id, start time, mode, scope, workload, paths, lens and, once the shards are planned, the ledger folder; it is written in Step 4 and completed in 5a), otherwise the one named in a previous partial Coverage Audit. **Check that it matches the request before using anything in it:** the same workload (name or description) and analyzed paths, the same mode, scope and lens, and, when a run id is named, the same run id; every item the request states must match the pointer. When it does not match, or the scratch directory is gone, say so in one sentence (and on the Coverage Audit's run line), move the pointer and the earlier deliverables aside, and start a new run from Step 1 (a different scope is a new run). A matching directory with a `corpus/progress.md` and a valid `corpus/manifest.json` is the same run: do not redo Step 4 and do not change the mode or scope. If `corpus/manifest.json` is missing or not `valid: true`, redo Step 4 in the same scratch directory; if it is valid but `corpus/progress.md` is missing, continue at 5a.
2. Read `corpus/workload.md`, `corpus/shards.md` and `corpus/progress.md`. Continue from the first shard in `corpus/shards.md` order that has no line in the progress file; shards that have a line are never read again. If a shard file exists for a shard with no line (the run stopped between the two writes), check that the file holds one block per BP and ends with its `Self-check:` line: if it does, append its line (and the tallies) to `corpus/progress.md` from the file; if it does not, redo the shard and overwrite the file.
3. If every shard has a line: when the progress file has no `Spot-check:` line yet, rerun the whole spot-check and overwrite `spot-check.md`; when `spot-check.md` lists a failed shard with no redo lines after it, redo that shard (5c, step 4); otherwise go to Step 6, or to Step 7 when `corpus/findings.md` exists, and write the report from its first part.
4. If `corpus/workload.md` or `corpus/architecture.puml` is missing, or `corpus/workload.md` has no `Embedded instructions:` line, rebuild the discovery summary, the diagram and that line from the workload before judging any shard: re-scan the workload content for every embedded instruction as the [discovery procedure](discovery-procedure.md) defines (each with `file:line` and a short quote, or `none`), because the resumed report's `Review Integrity:` line and its review-integrity findings come from that line. Ask the user if the workload is no longer available.
5. Report parts from an earlier PARTIAL report, or from a run stopped while writing the report, describe the earlier state: the resumed run rewrites `aws-well-architected-review-report.md` from its first part.
6. The resumed run keeps the pointer's run id and start time: append a `Resumed: {UTC time}` line to `corpus/progress.md`, and the Coverage Audit's run line carries the run id, the start time and each resume time. Every count, `BP pages read` included, covers this run id's own shard files only: a shard file whose header names another run id is not this run's evidence, so redo that shard.

## A failed or dropped read connection is never fatal

The MCP documentation connection can drop mid-run (a timeout, a restarted server, a closed session). That is a read failure, not a reason to stop, to judge from titles, or to restart:

1. Keep everything on disk as it is (finished shard files, the progress file).
2. Retry the shard's read once. If `aws___read_documentation` returns an error for a URL, read that URL with the HTTPS web-fetch tool (`retrieval_method` `web_fetch`, with the raw MCP error). A mixed run is allowed; the Coverage Audit records `retrieval_method` per BP.
3. Only when neither tool can read pages, stop at the shard boundary as described below: the PARTIAL report with exact coverage and `corpus/progress.md` for resuming. A transport failure, timeout or closed session is never `page_unreadable`. `page_unreadable` is only for a page where a tool actually returned one of the enumerated error codes for that URL (with the real error), and it counts toward the cap.

## Stopping early (only when forced)

Stop starting new shards only when a real limit is reached: the client has actually reported a context, token or output limit error, or the context is demonstrably near its documented limit (the client shows the usage, or states the window size and your usage is within about 10% of it) and cannot be compacted, cleared or reset; the environment or task states a wall-clock, turn or budget limit that the remaining shards would exceed, or the client or user signals that it is ending (a warning, a request to wrap up, a tool call killed for exceeding a limit); a tool fails repeatedly on every available read path; or the user says stop (also up front, for example "only SEC01 and SEC02 this session": stop once those questions' shards are done). A guess about context is not a limit: page bodies are not kept after a shard's line is written (rule 6), so without one of those signals, continue with the next pending shard. A failed self-check is never a reason to stop (it is recorded, [evaluation procedure](evaluation-procedure.md), 5c). **Time rule.** When a wall-clock limit is stated (or a tool call is killed for exceeding one), take the start time from the `started_at` key of `.wa-review-run` (written when the run directory is created, and copied into the progress header), check the clock at each shard boundary, and once the next shard would not finish with margin (less than about 15% of the limit left, enough to write the PARTIAL report) stop at that boundary and deliver the PARTIAL report below, which is the correct outcome, not a failure. A limit that nobody stated is not guessed: an unannounced time cap is not a reason to stop early. Effort, convenience, length, the number of shards remaining, or your own estimate of the effort, tokens or time still needed are not reasons, and a full or pillar-scoped review is never downgraded to quick mode.

**A stated limit shortens the run, never the scope.** A time, turn or budget limit, or a session limited to named questions, never changes the mode, the in-scope set or `N`: they stay those of the requested review (a full review keeps every manifest BP in `N`, for example 307, never the count of the pillar or questions the limit reaches, and it is never re-scoped to a pillar-scoped or quick review). The named questions' shards come first ([evaluation procedure](evaluation-procedure.md), 5a); when the limit is reached, the run stops at that shard boundary and delivers the PARTIAL report below, with `BP pages read: n / N in scope (PARTIAL: k not yet reviewed)`, what was read (the reviewed questions, and their BPs in the compact ledger), what remains (the unreviewed BP IDs, or every pending shard with its BP IDs) and the stated limit as the reason.

**When a real limit is reached, the PARTIAL report is the final message.** Stop reading, assemble the report from `corpus/progress.md` and the shard files (not from memory), and send it as your final message. A progress note, a summary, a list of next steps or a pointer to a file is never an acceptable final message, however little time is left; when time is short, write the report in the Compact or Minimal tier (Budgets, below), which keeps every section and every BP ID. At a shard boundary:

1. Make sure `corpus/progress.md` has a line for every finished shard, then write the report parts for what was reviewed (the summary states that the review is partial; the findings and plan cover reviewed BPs only).
2. The **PARTIAL** report has: a PARTIAL REVIEW banner that ends with `Say "continue the review" to resume run {run_id}.`, `Review status: PARTIAL` with reviewed/total BPs and shards, the exact `BP pages read: n / N in scope` (`N` the requested review's in-scope count, never narrowed by a stated limit), the `Review Integrity:` line, the reviewed questions and the list of unreviewed BP IDs, every in-scope BP ID in the compact ledger (unreviewed ones marked NOT REVIEWED), the ledger folder, and the run directory to resume from. Keep that directory, the ledger folder and the `.wa-review-run` pointer (none is deleted on an early exit); the resume works in the same working directory, and a new review request starts a fresh run.
3. **It is a useful report, not a placeholder.** The Pillar Scorecard gives a score (1-5) to every pillar whose in-scope BPs were all read; a pillar partly read gets a score labelled `provisional (k of N BPs read)` (k read of its N in-scope BPs), based only on the read BPs plus the stated workload evidence; only a pillar with no BP read is `not scored`. The Overall Maturity is labelled provisional in the same way. The findings include every workload-specific gap found in the read BPs (with its quoted BP element and `file:line` evidence, as in a complete report) and one review-integrity finding per embedded instruction, and the Eisenhower plan covers them.
4. Never claim completion, never fill unreviewed BPs from titles or memory, never score a pillar from BPs that were not read, and never drop a BP ID from the ledger. If even the report parts cannot be written, the final message still states the review is partial, the counts from `corpus/progress.md`, the `Review Integrity:` line, the pending shard IDs and the resume sentence.

## Build the report in parts

Write `aws-well-architected-review-report.md` in the working directory section by section (Step 7 in `SKILL.md`): create it with the first part, then append each further part; when the file tool cannot append, insert each part after the file's current last line with its edit operation, sending only the new part, never rewriting the file. Take the finding IDs, counts and quadrants from `corpus/findings.md` (Step 6) and the diagram from `corpus/architecture.puml` (written in 5a; quick and degraded runs keep it from discovery), and read the ledger files that hold gap rows a few at a time while you write the findings. Before sending, check every BP ID you cite against `corpus/progress.md`: no invented or unreviewed ID, and every Critical/High gap row cited by a finding.

## After the report

The final message is the report read back from `aws-well-architected-review-report.md` and the Step 8 offer (see the Final-message check in `SKILL.md`); it is never a hand-written summary of the ledger, never points to a file instead of containing the report, and never names the scratch directory, except the run directory a PARTIAL report names for resuming. Only a PARTIAL report as defined above may stand in for the complete one. If a late event arrives after the report (a timer, a background-task or worker notification), reply with the complete report again from `aws-well-architected-review-report.md` and the offer; a status note is a failed deliverable.

## Redundant calls to avoid

- One read of the TOC (about 3 slices); never rebuild the manifest during evaluation or on resume.
- One read call per shard; never one call per URL, never a search call to find a BP page whose URL is in the manifest.
- Never re-read a page to repair a format slip (quote length, wrong field) while its text is still in context; never paginate from the start unless you are retrying that page.
- Never re-read pages of a finished shard except those in the fixed spot-check sample, and never run a second verification pass over the same rows.
- Never write a row twice for the same BP unless its self-check failed or its shard is redone after a failed spot-check.
- Never re-read or retype ledger rows to build the report beyond the gap rows a finding quotes.
- Never copy page bodies into files or messages; the quotes in the rows are the only page text you write.

## Budgets (guidance for any client; they are not tuned to a harness)

| Item | Emitted in one message |
| ---- | ---------------------- |
| An inventory file | one pillar, about 1.5-3K tokens |
| A shard file | at most 5 rows, about 1-1.3K tokens (average under 260 tokens per BP) |
| A progress update | one appended line, about 100-150 tokens (the whole file is about 4-5K tokens for the whole framework, written only by a client that can neither append nor insert) |
| A shard read | one tool response, typically 20-30K characters (about 5-8K tokens of input) |
| `corpus/workload.md` | about 1K tokens |
| One report part | about 2K tokens |
| Final message | the report: about 14 tokens per BP line, about 40 per question row, plus your parts |

The compact ledger and the per-question table are bounded by the number of BPs and questions (about 14 tokens x BPs plus 40 x questions; roughly 7K tokens for the whole framework at the time of writing); the rest is your parts, which the size limits in [the report template](../assets/report-template.md) bound. Every tier keeps **every section of the report template, the Coverage Audit's `Review Integrity:` line and every BP ID**; the tiers shrink prose only. Pick the tier that fits the client's single-message limit, when you know it (when you do not, use Standard):

1. **Standard** (roughly 15-25K tokens for the whole framework): one line per BP, parts at the template sizes.
2. **Compact** (roughly 9K): the compact ledger grouped by status and risk (every BP ID still present, for example `Partially Implemented / High: SEC02-BP01, REL09-BP03, ...`); Medium and Low findings as one table row each, each with a short quoted BP element; the plan as tables.
3. **Minimal** (roughly 6K, last resort): the same sections at minimum prose: a three-line summary, Critical and High findings in one or two lines each, Medium and Low findings as table rows (BP ID and a few words), trade-offs and Next Steps in a line or two each. Never omit a section, never truncate silently, never drop a BP ID, and keep the single final message.

The complete report is always in `aws-well-architected-review-report.md`, so a report that the client cut short or lost can be re-sent in full from that file.

**Output cap below the Minimal tier (about 6K tokens).** This applies only when the client's single-message limit is known to be below about 6K tokens and you can name that limit; a long report (30K characters or more) is not a reason to point to a file, so send it inline. When it applies, no tier fits one message. Say so in the first message and give the path of the report file there, then send the report from that file as consecutive messages, in order and each under the cap, split at section boundaries (read a slice, copy it, read the next); the first message starts with `# Well-Architected Review:` and the Coverage Audit comes first, and the last ends with the Step 8 offer. The single-final-message rule yields to the client's cap here, and nothing is left out or summarized.

Quick mode and a degraded run have no ledger: write the per-question table in parts of at most 20 questions.
