Current Stack Overview ↑ contents

Discovery read 15 resources from the Render Blueprint: one project with one production environment, four compute services, two data stores, one persistent disk, one static site, one custom domain, one environment group, one Build Source, and one Workflow with one task. Design mapped all 15: 13 receive generated Terraform or scripts and 2 (the project and the environment) are consumed as account and network topology rather than becoming a resource of their own.

  • Web service (public, custom domain, 1 vCPU, 2 GB, two tasks) and a private service reached only through service discovery
  • Background worker (continuous queue consumer) and a cron job that runs for about 20 minutes
  • PostgreSQL (Multi-AZ requirement, pgcrypto extension, writer only, under-15-minute downtime tolerance)
  • Key Value store (stable 3 GB capacity, persistence off, empty-start migration)
  • Persistent disk mounted at /var/data with shared POSIX access
  • Static site served from a publish directory with no server process
  • Custom domain with externally owned DNS and TLS terminated by Render today
  • Environment group of shared configuration names (secret values are never captured)
  • Build Source feeding several environments from one immutable build
  • Workflow with auditable history and callbacks, plus one five-minute stateless Workflow task
  • Project and environment boundaries (consumed as topology: account, VPC, and isolated deployment stack)

Architecture Overview ↑ contents

The design uses build-once immutable promotion through Amazon ECR, managed PostgreSQL on Amazon RDS and managed Valkey on Amazon ElastiCache, ECS on Fargate for direct task control, a private service-discovery path with no public load balancer for the private service, and Amazon S3 with CloudFront for the static site. Project and environment boundaries become tagged, isolated network and deployment stacks inside one AWS account. Secrets and non-secret configuration move to AWS Secrets Manager and Systems Manager Parameter Store without copying values.

Fargate deployment mode per service: rr-web is standard with a hand-built ALB (custom_domain_alb) and its default canary release becomes a rolling update; rr-private is standard (private_discovery); rr-worker is standard (no_http_listener); rr-cron is standard (no_http_listener). No service uses ECS Express Mode.

  • Delivery: GitHub Actions assumes an OIDC role, pushes one immutable digest to ECR, and promotes that digest to each environment tag without rebuilding
  • Compute: four Fargate workloads (web, private, worker, and a scheduled RunTask for the cron job); the Workflow runs on Step Functions Standard with a Lambda task
  • Data: Multi-AZ RDS for PostgreSQL migrated by AWS Database Migration Service; a node-based ElastiCache for Valkey cluster started empty
  • Storage and edge: an encrypted EFS access point for /var/data; S3 behind CloudFront for static assets; an ACM certificate while DNS stays external

Data Migration ↑ contents

Verify PostgreSQL version, extensions (pgcrypto), source privileges, connection pooling, and connectivity before selecting AWS Database Migration Service for full load and change-data-capture; the under-15-minute downtime tolerance rules out dump-and-restore. Rehearse schema and full load in an isolated target, start change-data-capture only after the privilege preflight passes, and monitor lag. At cutover, perform writer quiescence, apply the final delta, run row-count and checksum integrity checks, then switch the application connection. Validate Valkey command, persistence, and eviction semantics without capturing values; the Key Value store starts empty, so no data is copied. Keep explicit source retention until sign-off.

Storage Migration ↑ contents

Create the encrypted EFS access point for /var/data; verify ownership, permissions, locking, latency, file count, and capacity against the real footprint, not only the 5 GB Blueprint value. Run a pre-copy, then writer quiescence and a final delta. Compare the checksum integrity manifest before remounting the Fargate tasks. Retain the source disk for rollback. Do not substitute EBS for Fargate.

Deployment Migration ↑ contents

Build once in GitHub Actions and push one immutable ECR digest, then promote that digest to each environment tag without rebuilding; deploy the digest reference, not the tag. Record the serving deploy identity separately from the newest deploy, preserve auto-deploy state, and retain rollback lineage before shifting any environment. The private service, worker, cron task, and Workflow task packages follow the same digest-first rule.

Cutover ↑ contents

Confirm prerequisites and certificate readiness (the ACM certificate must report Issued before the listener is applied), lower external DNS TTL 24 hours in advance, freeze releases, establish writer quiescence, apply the final data deltas, verify private service discovery, disable the Render cron before enabling EventBridge Scheduler, switch Workflow callers, then switch traffic once inside the short planned maintenance window with traffic stopped. DNS remains external; nothing fabricates Route 53 ownership. Hold the window until acceptance checks pass.

Rollback ↑ contents

Use error rate, integrity mismatch, unacceptable lag, and failed behavior checks as rollback triggers. Fence target writers before restoring the retained Render source writer, restore DNS and traffic to Render, preserve target evidence, and honor the source retention window of 14 days after cutover and until sign-off. Never allow two PostgreSQL primaries. Key Value rollback cannot merge writes made on AWS.

Verification ↑ contents

Check public and static endpoint responses, private endpoint reachability, database read/write and reconciled counts and checksums, cache eviction and persistence behavior, disk ownership, permissions, locking, and integrity, worker drain/retry/idempotency, cron overlap policy, and that the running image digest is the promoted ECR digest. Run Workflow executions and confirm the declared retries with their backoff, the per-attempt timeout, the task-token callback completing inside its wait, retained execution logs, and the three Workflow alarms pointing at an owned notification target.

Appendix C — Migration Steps and Rollback ↑ contents

Phases follow the sequence in MIGRATION_GUIDE.md. Every script under scripts/ is dry-run by default and takes --execute to act; none was executed during Generate. Durations are not quoted; stage order and the verification gate after each phase carry the schedule.

Phase 1 — Prerequisites

  • Configure AWS credentials, confirm us-east-1, install Terraform 1.5 or newer, and bootstrap remote state before normal initialization
  • Populate target secrets without copying values into Terraform or the guide; the CI role assumed through OIDC pushes to ECR without long-lived keys
  • Confirm PostgreSQL version, extensions, replication privileges, network paths, and the maintenance window
  • Request the public web certificate in ACM, create every DNS validation record at the external DNS provider, wait until ACM reports Issued, and supply the ARN before applying the stack
  • Create the IAM Identity Center directory and re-invite the team; define source-retention and rollback owners

Phase 2 — Build and deployment migration

  • Run scripts/promote-image.sh ECR_REPOSITORY_URL SHA256_DIGEST TARGET_ENVIRONMENT to preview promotion (dry run), then repeat with --execute
  • The helper verifies an immutable ECR repository, resolves the exact source digest, and creates the environment promotion tag from that manifest without rebuilding
  • Deploy the repository@sha256:... reference, not the environment tag; record the serving deploy separately from the newest deploy

Phase 3 — PostgreSQL migration

  • Run scripts/migrate-postgres.sh (dry run) to print the full-load and change-data-capture stages, then with --execute only after confirmed writer quiescence
  • Rehearse schema and full load in an isolated target; start AWS Database Migration Service change-data-capture after the privilege preflight; monitor lag
  • Establish writer quiescence, apply the final delta, compare row counts and checksums, switch the connection, retain the Render source until sign-off

Phase 4 — Key Value migration

  • Verify supported commands, persistence, eviction, pub/sub, streams, and Lua behavior on the ElastiCache for Valkey node
  • Empty start: no data is copied, so queued and session data is lost at cutover; validate key-count and sample behavior without recording values

Phase 5 — Persistent-disk migration

  • Create the encrypted EFS access point for /var/data; check capacity, ownership, permissions, locking, file count, and performance
  • Run scripts/migrate-disk.sh (dry run) for the pre-copy plan, then with --execute; quiesce writers for the final delta, compare the checksum manifest, remount, retain the Render disk

Phase 6 — Deployment and service cutover

  • Verify private service discovery before public traffic; drain the worker and preserve graceful shutdown and idempotency
  • Disable the Render cron before enabling EventBridge Scheduler, preventing overlap; restore desired counts and pass health checks
  • Workflow: upload the reviewed Lambda package and set its runtime, handler, and memory variables; replace each Render caller with a Step Functions start-execution call; grant the callback sender its task-token permissions outside Terraform; stop Render runs before enabling the AWS callers

Phase 7 — DNS and traffic cutover

  • Lower external DNS TTL 24 hours in advance; freeze releases; quiesce data writers; complete final deltas
  • Switch traffic once inside the planned maintenance window with traffic stopped; the short window selects a single switch, not staged shifting

Phase 8 — Verification

  • Static, public, and private endpoints; database round-trip with reconciled counts and checksums; cache eviction and persistence; EFS ownership, permissions, locking, integrity
  • Worker drain/retry/idempotency; cron overlap policy; running image digest equals the promoted ECR digest
  • Workflow executions show the declared retries with backoff, the per-attempt timeout, and the task-token callback completing before its timeout; the three Workflow alarms exist and point at an owned notification target
