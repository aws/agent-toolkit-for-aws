# Direct decision report assembler

Validate `references/runtime/content-contribution.schema.json`, consume `references/report-sections/ai-decision-report.md`, and submit both final targets through `scripts/bma-runtime.py execute --request -`. The production entrypoint rejects duplicate IDs/order keys and an existing target unless the request carries that file's current SHA-256 as `expected_sha256`, sorts by bucket/source_order/UTF-8 ID, selects the direct writer, and performs each write. Run `scripts/emit-plan-json.py` after the successful decision writes.

Report assembly ABI: every assembly passes `phase`, `target`, `contributions`, and a complete controller-supplied `document`. The document holds one `<!-- bma-contributions:<section-id> -->` anchor for each section that receives contributions. HTML targets also pass `report_mode`: `migration-report.html` takes `full` or `ai_only`, and `decision-report.html` takes `decision`. Each contribution carries a `section` that names its anchor. The runtime preflights the document structure, renders contribution text as escaped paragraphs (callouts as `<p class="callout">`), inserts each contribution at its anchor, and performs the only final write. A request that sends contributions without `document` fails with `document_required`; a missing anchor fails with `contribution_anchor_missing`; a document that fails the structure check fails with `document_structure_invalid`. To regenerate an already-written final target (for example after re-entering Estimate or Generate), pass `expected_sha256` = SHA-256 of the exact prior bytes on the assembly; the runtime applies the same owner, owning-phase, prior-hash, same-request-duplicate and rollback rules as `writes[]`. Without the hash a rerun fails `duplicate_final_write`; a stale hash fails `expected_prior_hash_mismatch`.
