# Troubleshooting

Match on the exact error string, then apply the fix. The key distinction: **warmup/transient errors should be retried; `client_disconnected` should not** — it means the session is gone.

## Error string → cause → fix

| Error | Cause | Fix |
|---|---|---|
| `dcv session not ready` | Desktop still connecting after the streaming URL was created (5–30s, sometimes longer). | Retry with backoff. The service retries connection readiness for up to ~10 minutes; wait and retry rather than failing. |
| `Unknown tool` (right after connect) | DCV desktop session not fully connected yet, so tools aren't registered. | Same as above — poll/retry until tools appear (or use POLLING mode + `connection_status`). |
| `backend unavailable` | Transient service issue. | Retry briefly (a handful of attempts). |
| `client_disconnected` | The session was **stopped, or the auth (streaming URL / SAML assertion / federated role credentials) expired or was revoked** — the user or orchestrator ended it, or it timed out. | Do **not** just retry the same connection. Reconnect with **fresh auth** — a new connection with the stack and user ID headers or a new streaming URL (non-domain-joined), or new federated credentials or a new SAML assertion (domain-joined). |
| `400` naming a duplicate input | The same input (e.g. the stack ARN) was sent both as a header and in `_meta`. | Send each input once, in the header or in `_meta`. |
| `400 Bad Request` | SigV4 **signing region does not match the fleet region** (cross-region). | Sign for the fleet's region — set `AWS_REGION`/the MCP signing region to the fleet region and use the matching regional endpoint. |
| `401 INVALID_AUTH_POLICY` (domain-joined) | The federated role lacks `appstream:Stream` on the stack. | Allow `appstream:Stream` on the exact stack ARN the agent sends. |
| `401 Unauthorized` | SigV4 signing failed / credentials can't sign. | Check AWS credentials (`aws sts get-caller-identity`); verify the correct profile is used for MCP signing. |
| `403 Forbidden` | Missing IAM permissions for Agent Access, or a stack ARN from another account. | Grant the specific `agentaccess-mcp` actions the agent calls (e.g. `InvokeMcp`, `GetScreenshot`, `LeftClick`, `TypeText`; add `CallForwardedTool` for forwarding), scoped by the `agentaccess-mcp:StackArn` condition key, or `agentaccess-mcp:ImageBuilderArn` for a builder — avoid a blanket `agentaccess-mcp:*` (see connection-setup.md). The stack must be in the caller's account. |
| `403 Forbidden` on `execute_sequence` | The caller is denied `ExecuteSequence`, `GetScreenshot`, or the action of any one step. The whole sequence is refused, and no step runs. | Allow `ExecuteSequence`, `GetScreenshot` and each step's action (see connection-setup.md), or remove the step that is denied. |
| `404` on a domain-joined session | A request named a different stack than the one the session started on. | Keep sending the session's own stack ARN, or start a new session for the other stack. |
| Domain-joined desktop logon fails (e.g. `Domain logon rejected`) after the session is created | The federated session's AD identity is missing or wrong: no `UserPrincipalName` or `ObjectSid` tag, a UPN not in `user@ad-dns-name` form, or a SID that is not the AD user's. Also a CBA prerequisite problem. | Inspect the `principalTags` (and, for SAML, the `NameID`) on the `AssumeRoleWithWebIdentity` or `AssumeRoleWithSAML` CloudTrail event, fix the IdP claim or attribute mapping, then check the CBA prerequisites. |
| `AccessDenied` or `InvalidIdentityToken` from `AssumeRoleWithWebIdentity` | A required tag is missing from the token (with `Null` conditions in the trust policy), the IAM OIDC provider URL does not match the token's `iss`, or a tag claim has the wrong shape (for example `transitive_tag_keys ... is not a list`). | Decode the token and check the tag claims first: tag values and `transitive_tag_keys` must be arrays. Then check the provider URL and audience. |
| `DCV proxy not initialized` | Nothing named the session: no stack header, streaming URL, stack ARN, SAML assertion or image builder name. | Pass the stack and user ID headers or the streaming URL header (non-domain-joined), the stack ARN with federated credentials or the SAML `_meta` (domain-joined), or the builder name and local user (image builders), or connect via a Gateway that auto-provisions. |
| `_meta.screenshotUploadError` on a screenshot result (`Unable to write screenshot ...`) | Screenshot storage is on, but the upload failed: usually the signing identity lacks `s3:PutObject` on the bucket, or `kms:GenerateDataKey` on its customer managed key. The screenshot itself still returned. | Grant the missing permission (connection-setup.md, Screenshot storage). The error names the screenshot's S3 key and the bucket, but not the reason, so check the permissions first. |
| `No available capacity on the fleet` (HTTP 503) on the stack and user ID path | The server checks for a free desktop before it creates the session, and a desktop this user ID is already using doesn't count as free. On a fleet whose only desktop the agent holds, reconnecting with the stack and user ID headers fails this way. | If `describe-sessions` shows an active session for this user ID, connect with a streaming URL from `create-streaming-url` for the same user ID, which attaches to that session. Otherwise wait for a desktop, or raise the fleet's capacity with the `setting-up-workspaces-applications` skill. |
| A coding agent's Agent Access server shows no desktop tools | The client started the server before the fleet had a desktop available or the builder was `RUNNING`, so the first connect failed, and it doesn't retry. | Reconnect the server once the environment is ready (connection-setup.md, From a coding agent's MCP config). |
| `InvokeMcp is not allowed for local user: ...`, or a local-user error, on an image builder | The Windows account is missing, invalid, or not allowed by the IAM policy. | See image-builders.md, Errors specific to builders. |
| Forwarded tool returns an error string | Often a path outside the sandbox, or the 5s tool-call timeout. | Read the error; fix the argument (keep paths in the server's sandbox) and retry once. Ensure the tool returns within 5s. |
| `tools/list` shows the standard tools although the computer use interface header was expected | The client did not send the header on `tools/list`, or interface selection is not enabled for the caller. | Send `x-amzn-agentaccess-computer-use-interface-id: ANTHROPIC_COMPUTER_20250124` on `tools/list` and every related `tools/call`. During rollout, a caller not enabled for interface selection receives the standard tools without an error. Confirm current availability in the Agent Access documentation (see computer-use-interface.md). |
| `Unknown computer use interface: '...'` or JSON-RPC `-32602` after selecting an interface | The header value is unknown or has different casing. | Use the exact case-sensitive value `ANTHROPIC_COMPUTER_20250124` (see computer-use-interface.md). |
| `Replay Session enabled but action blocked due to internal service error.` | Replay Session could not capture or store the frame for this action, so the action was **not run** (capture is fail-closed). | Retry the action once. If it repeats, end the session and report the MCP session ID to AWS Support. See replay-session.md. |
| `Replay Session enabled but action blocked. The customer managed key call failed. KMS returned ... for ...` | The stack's `KmsKeyArn` cannot be used: the key policy denies the call named in the message, or the key is disabled or pending deletion. The action was not run. | Fix the key using the KMS error code and operation in the message: enable the key, and in the key policy allow, when called through Agent Access: the agent's own IAM identity (the one that signs its MCP requests) `kms:GenerateDataKey`, `kms:Decrypt` and `kms:DescribeKey`; and the identity that creates or updates the stack `kms:DescribeKey`. The key is used with these callers' forwarded credentials, not a service principal (see replay-session.md → Key policy). Retrying unchanged will fail again. |
| `Unknown parameter in AgentAccessConfig: "ReplaySessionEnabled"` (or `"KmsKeyArn"`) from the AWS CLI or SDK | The installed CLI or SDK predates the Replay Session fields and rejects them before sending the request. | Update the AWS CLI or SDK and rerun. This is not an account or stack problem. |
| No recording in the S3 bucket, or the transcript and report but no video | The MCP session has not closed yet, the session started before Replay Session was enabled, it was an image builder session, you are looking under the wrong date, or the agent's IAM identity cannot write to the bucket (no video alone usually means a missing `kms:Decrypt` on an SSE-KMS bucket). | Close the session with an HTTP `DELETE` and wait a minute; check the `day=` folder for the session's **start** date in UTC; confirm `ReplaySessionEnabled` is `true` on the stack; give the identity that signs the agent's MCP requests `s3:PutObject` on `agentaccess/replay-session/*` (and `kms:GenerateDataKey` and `kms:Decrypt` if the bucket default is SSE-KMS with your own key; the video is uploaded in parts, which needs both) (see replay-session.md). |

## Retryable vs fatal (client behavior)

- **Retryable** (wait + reconnect): `dcv session not ready`, `Unknown tool` at startup, `channel not connected`, `connection to the mcp server was closed`, `timed out`, `backend unavailable`. Back off (e.g. increasing delay) across a few attempts.
- **Fatal without fresh auth:** `client_disconnected` — reconnect: a new connection with the stack and user ID headers or a new streaming URL (non-domain-joined), or new federated credentials or a new SAML assertion (domain-joined).
- **Fix-then-retry (config, not transient):** `400` (signing region, duplicate input), `401` (credentials, `appstream:Stream`), `403` (IAM, cross-account stack), `404` (different stack on a domain-joined session), and a Replay Session customer managed key error — correct the cause; retrying unchanged won't help.

## Cold start note

The first tool call after a cold start can take 10–30s while the desktop connects. This is expected — build in a wait/retry rather than treating the first slow call as a failure.
