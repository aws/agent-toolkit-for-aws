# AgentCore Policy service rules

The rules the AgentCore Policy service applies to a statement, beyond the Dogwood language in
`dogwood-language.md`. Where the two differ, this file wins. Read it before drafting any
policy.

Rules marked † are not detected by `validate`: check them yourself before you submit, and
expect the service (at create or in live decisions) to be the first to show a violation.

## Before you write

- A request is allowed only when a `permit` applies and no `forbid` applies; an engine with no
  policies denies everything. Every tool needs a permit.
- Read the destination engine's existing policies first when the developer agreed
  (`describe --policies` after `policies load`, or `api list_policies` / `api get_policy`);
  without that agreement, do not stop: draft from the request, say they were not checked, and
  offer to load them. When an existing permit already
  covers the callers, write **only the restricting statement** (the `forbid`, guardrail or
  temporal condition); do not add a new or broader permit. Add a scoped permit only when the
  intended callers have none, and only with the developer's explicit approval.
- For "only X may call T", write one `permit` for X on T. Do not add a `forbid` for "everyone
  except X": deny-by-default already blocks them. An existing `forbid` beats any permit you add,
  and one broad permit on a tool cancels every conditional permit on the same tool. Do not
  narrow or rewrite existing policies unless the developer asks.
- "Allow X only when C" and the same restriction in other words ("X only if C", "X requires C",
  "X only after B", "never X unless C", "X must not happen unless C") is `forbid … unless { C }`
  on X, on every route, also when the existing permits are unknown. Do not write
  `permit … when { C }` for it (a broad permit on X makes that permit add nothing, so X is
  allowed without C, with no finding), and do not add a permit to pair with the forbid. "Allow
  X when C" without "only" is `permit … when { C }`. Pure caller rules ("only X may call T")
  keep the rule above.
  - Subject and requirement: a qualifier of the request BEFORE "only if/only when/requires" is
    the rule's subject and goes in `when`; everything AFTER it is the requirement and goes in
    `unless`. "Retrieving lab results that include preliminary findings is permitted only if
    the user authenticated within 2 hours" → `forbid … when { <preliminary findings> } unless
{ <authenticated within 2h> }`: other lab results are not affected. "Adding a note is
    permitted only when the note is marked confidential and the claim was reviewed" → both
    conditions come after "only when", so both go in `unless`.
  - Existing permits known (Gateway route, after `policies load`): when no loaded permit
    covers the callers of X and the developer wants to grant X, you may offer `permit … when
{ C }` instead (exact in this engine). Say that it fails open if someone adds a broader
    permit on X later, and write it only with the developer's approval. In every other case,
    and always in document mode, use the forbid.
  - The forbid restricts every caller of X, also callers that another permit allows. When
    another rule of the same request or document, or a loaded existing policy, permits X on its
    own condition ("admins may always refund"), the forbid blocks that permit: this is a
    conflict. Never merge the policies or change either condition yourself. Show the developer
    both statements and the requests that the forbid blocks, and ask which they want: keep the
    forbid as written (it applies to everyone), or add the other condition to the `unless`
    (`unless { C || <other condition> }`). Store the forbid draft with `--review-required
"blocks the permit of <rule>"`; the submission gate refuses it until `draft resolve --id
<draft-id> --resolution "<their decision>"` records the developer's choice.
  - When no permit covers X, the create fails with "Overly Restrictive" under
    `FAIL_ON_ANY_FINDINGS`: report that X has no permit (missing authorization). Do not submit
    again with `IGNORE_ALL_FINDINGS` to make it pass, and do not add a permit without the
    developer's approval.
  - In the report, say for each such policy that it applies to all callers of X.
- Take every identifier (target and action names, the Gateway ARN, claim keys) verbatim from
  the `prepare` / `describe` output. `describe` lists tool names without the target prefix: add
  `<target>___` yourself, but do not double it when a name already has it (as in Gateway
  `tools/list`). A name that matches nothing is a wrong name, never "an action without input".

Guarded tag reads (`principal.hasTag(k) && principal.getTag(k) …`) work on a bare `principal` and need no type; keep it bare, so a `forbid … unless { claim }` still blocks callers without the claim | `principal is AgentCore::IamEntity`                                                                                                                                  |

Do not use the IAM role ARN or the role id. When the request names both the account and the role or user (for example "the IAM role OrdersReader in account 111122223333"), the ARN is determined: write `arn:aws:sts::<account>:assumed-role/<RoleName>` (or `arn:aws:iam::<account>:user/<name>`) and list it as an assumption; otherwise ask the developer once, for all rules. Never derive an ARN from a label such as "admin users". "Any role in account A" is `like "arn:aws:sts::A:assumed-role/*"` †                                                                                                                                                                                                                                                                                                                                           | `principal.id == "arn:aws:sts::111122223333:assumed-role/OrdersReader"`                                                                                              |

## Temporal policies

| Rule                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                      | Example                                                                                                                                                                                                                                                                                     |
| ----------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| Every event predicate has `eventResource: resource` (also a bare predicate). Write it yourself until `draft put` adds it                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                  | `…"T___refund"::error{ eventResource: resource }`                                                                                                                                                                                                                                           |
| `unless temporal { … }` is accepted, also next to a `when` clause; it is how an exception to a history rule ("… unless approved recently") is written                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                     | `forbid (…) when { … } unless temporal { formerly within 5m …::response{ eventResource: resource } };`                                                                                                                                                                                      |
| At most 3 temporal operators per policy (`formerly`, `previous`, `since`, `count`, `sum` all count) †                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                     | `count` over `formerly` = 2                                                                                                                                                                                                                                                                 |
| Every evaluated call records `::request`, also a call that a policy denies. A denied call, or a tool result with `isError`, also records `::error`; a successful call records `::response` (only while the Gateway is in `ENFORCE`). So "succeeded / completed / was prepared" needs `::response`, "failed or denied" is `::error`, and a `::request` count includes denied retries †                                                                                                                                                                                                                                                                                                                                                                                                                                                     | "after 3 denied refunds" counts `…"T___refund"::error{ eventResource: resource }`; "a draft was prepared" is `…"T___draft"::response{ … }`                                                                                                                                                  |
| The current call is part of its own history: `formerly` (and `count` / `sum` over it) on the current action's `::request` includes the current call, so after k earlier calls the count is k+1, and a bare `formerly` on the current action with pins the call itself meets is always true. `previous` does not see the current call; it sees the single event before it (usually the prior call's `::response` or `::error`, not its `::request`). So "the immediately preceding action was X" is `temporal { previous within W X::response{…} } \|\| temporal { previous within W X::error{…} }`; `previous X::request` alone matches only while X is still running. For a count threshold this is already in the convention of `dogwood-language.md` ("already N" and "more than N already" are both `n > N`); do not add a second 1 † | "deny a 2nd refund for the same order within 1h": `count … formerly within 1h (…"T___refund"::request{ input.order_id: context.input.order_id, eventResource: resource } && tp(t)) … n >= 2`                                                                                                |
| `output.<field>` exists only on `::response` and only if the target declares an output schema; an undeclared event field is rejected and the message lists the declared fields                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                            | correlate on `input.*` when there is no output schema                                                                                                                                                                                                                                       |
| Each tool's enum field has its own enum type, also when two tools declare the same values. So a temporal predicate cannot correlate one tool's enum field with another tool's enum field in the current call: `input.subject: context.input.subject` across two tools is a type error. Write one policy per enum value instead, and pin the value on both sides with each tool's own type. This is exact only when both enums have the same values: a value that only the current tool has gets no policy (with a `permit`, its requests are not allowed; with a `forbid`, they are not denied), and a value that only the other tool has cannot match. List the expansion and both value sets in the report. A correlation between fields of the same tool works directly                                                                | "only if a lesson plan for the same subject was generated" → one `permit` per value, each with `when { context.input.subject == AgentCore::<type of tool A>::"math" }` and `…generate_lesson_plan::response{ input.subject: AgentCore::<type of tool B>::"math", eventResource: resource }` |
| Inside `temporal { … }`, `<` `<=` `>` `>=` work only on `Long`; decimal methods do not parse there; equality works on every type; `sum` sums `Long` only (a `sum` over a `decimal` field is rejected at create: "sum requires a `Long` summand, but `a` is `Decimal`")                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                    | `input.amount: decimal("10.0")` is accepted; `a > decimal("10.0")` is not                                                                                                                                                                                                                   |
| "X is in progress" (started, not yet completed) has one accepted exact form, the split form: `previous within W ((!X::response{…} since within W X::request{…}) && (!X::error{…} since within W X::request{…}))` (without `previous` when X is not the current action). A failed or denied X records `::error` and never `::response`, so `!X::response since …` alone denies X after one failure until W ends; `(!X::response && !X::error) since …` fails at create ("An internal error occurred during creation"). The split form uses 3 temporal operators (2 without `previous`) †                                                                                                                                                                                                                                                   | see `dogwood-language.md`, "X is in progress" idiom                                                                                                                                                                                                                                         |
| History is per policy session (the `sessionId` pin), at most 24h back; a count cap resets in a new session, so it is not a security control                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                               | —                                                                                                                                                                                                                                                                                           |
| Temporal policies need the client to send the `x-amzn-bedrock-agentcore-policy-session-id` header. The client chooses the id; the Gateway does not generate one. Use one id for each agent session, without `#` or `_` (HTTP 400), and pass it on to Runtime calls that call the Gateway again. Without it, calls are denied ("sessionId is required when temporal policies are enabled"). The Gateway role needs `bedrock-agentcore:GetWorkloadAccessToken`. Create temporal policies one at a time. Tell the developer before submission †                                                                                                                                                                                                                                                                                              | —                                                                                                                                                                                                                                                                                           |

## Conditions and types

| Rule                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                           | Example                                                                                       |
| ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------ | --------------------------------------------------------------------------------------------- |
| Reading an optional field in a Cedar condition needs a `has` guard; an unguarded read is rejected at create (a guardrail argument is the exception: see Guardrails). With the guard, an absent field makes the guarded clause false. A call without a required field is denied by the engine                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                   | `context.input has note && context.input.note == "x"`                                         |
| MCP `integer` → `Long` (plain operators); MCP `number` → `decimal` (decimal methods); HTTP and inference overlay numbers → `Long`. Read `describe` → `context_types` for each field                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                            | `context.input.amount.greaterThan(decimal("1000.0"))`                                         |
| A field with a JSON-schema `enum` is an entity type, not a String: compare it with `context.input.<field> == AgentCore::<enum type>::"<value>"`, where the type is the generated `ID_<hash>_…_Input_<field>` name. Copy it from `describe --action <target>___<tool>` (`compare_with`); a string literal is a type error                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                       | `context.input.priority == AgentCore::ID_…_Input_priority::"high"`                            |
| On a Lambda target with an inline tool schema, `enum` is dropped, so the field is a plain `String` (`describe` shows `String`, with no `compare_with` and no list of values): compare it with a string literal, and the service accepts any value. A typo, a wrong case (`"High"` for `"high"`) or a value outside the tool's enum validates, reaches ACTIVE and never matches. Use only values that the developer confirms or that the rule names verbatim, and report the assumption ("assumes `high` is a value of `priority`"). When the rule means "only these values", write the check so that a wrong value denies: `permit … when { context.input.priority == "high" }` or `forbid … unless { context.input.priority == "high" }`, not `forbid … when { context.input.priority != "high" }`. A rule that blocks one value (`forbid … when { … == "low" }`) cannot fail closed, so confirm that value with the developer. Keep the effect that the other rules choose † | `forbid (principal, action == …, resource == …) unless { context.input.priority == "high" };` |
| Wall-clock rules read `context.system.now` in a plain `when`; they are not temporal policies                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                   | `context.system.now.toTime() >= duration("9h")`                                               |
| A date in a field that `describe` types as `String` is not a date: ordered or relative comparisons on it are non-translatable, and equality matches only the exact text (use it only with a format the developer confirms). Lambda targets with an inline tool schema drop `format: date-time` (and `enum`), so their date fields are `String`: `due > datetime("…")` fails at create there, and the same statement is ACTIVE on an OpenAPI target with the same tool †                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                        | see `dogwood-language.md`, time-based policies                                                |

## Guardrails

| Rule                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                   | Example                                                                                                                                                                               |
| ---------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| Write the aggregation method directly after the closing parenthesis of `SensitiveInformation(...)`, with no space or line break: with whitespace before `.maxConfidenceScore()` the service rejects the statement ("requires an aggregation method call"); `ContentFilter` accepts a line break                                                                                                                                                                                                                                                                                                                                                                                                                        | `SensitiveInformation(["EMAIL"], [context.input.memo]).maxConfidenceScore()`                                                                                                          |
| `SensitiveInformation` rejects per-category indexing; use `.maxConfidenceScore()`, `.minConfidenceScore()` or `.count()`                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                               | `SensitiveInformation(["EMAIL"], [context.input.memo]).maxConfidenceScore()…`                                                                                                         |
| The only supported information providers are the Bedrock Guardrails (`ContentFilter`, `PromptAttack`, `SensitiveInformation`) declared in the provider schema. Do not use Dogwood macros (`def cedar` / `def temporal`) or custom (Rust/Rhai) providers                                                                                                                                                                                                                                                                                                                                                                                                                                                                | —                                                                                                                                                                                     |
| Only the categories in `guardrail_providers.categories` (from `prepare` / `describe`) are valid; do not take names from the Bedrock Guardrails documentation. For "any PII", name every `SensitiveInformation` category listed there                                                                                                                                                                                                                                                                                                                                                                                                                                                                                   | `US_BANK_ACCOUNT_NUMBER`, not `ACCOUNT_NUMBER`                                                                                                                                        |
| Scores come in steps of 0.2 (`0.0` … `1.0`): `greaterThan(decimal("0.5"))` fires from `0.6`. Copy the developer's threshold verbatim †                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                 | "higher than 0.5" → `.greaterThan(decimal("0.5"))`                                                                                                                                    |
| With several categories, the bracket form screens only the indexed category †                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                          | `ContentFilter(["VIOLENCE","HATE"], …).maxConfidenceScore()` covers both                                                                                                              |
| A guardrail whose paths resolve to nothing denies the request ("request missing field(s) required for guardrail evaluation"), for example an omitted optional field or a wrong `$`-path. An unguarded optional field (or a field inside an optional record) as a guardrail argument is accepted at create, and `validate` reports it (`guardrail_unguarded_optional`), so guard every optional level yourself (`context.input has a && context.input.a has b`): in a `forbid`, `context.input has f && <guardrail check on f>` (an absent field is not screened and the call is not denied); in a `permit`, `!(context.input has f) \|\| <guardrail check on f>`. The guardrail is not called when the guard decides † | `forbid … when guardrails { context.input has note && BedrockGuardrails::ContentFilter(["VIOLENCE"], [context.input.note])["VIOLENCE"].confidenceScore.greaterThan(decimal("0.5")) }` |
| A field path must name a scalar string; a field path to a list or set is rejected. A string inside a nested record works as a Cedar path (`[context.input.delivery_address.special_instructions]`, also 2 levels deep; the guardrail screens only that field). Text inside a list (chat `messages[*].content`) needs a `$`-path, a JSONPath string over the raw payload; this skill uses them only on inference, HTTP and Runtime targets (on MCP targets such a rule is non-translatable). A `$`-path is not checked at create: if none of a check's paths resolves, every request in scope is denied (`agentcore-targets-and-effects.md`) †                                                                          | `[context.input.note]`                                                                                                                                                                |
| `permit` / `forbid` guardrails read the request; `context.output` under them is rejected. Response screening is `suppressOutput` (guardrail checks only, no Cedar or temporal conditions), which this skill writes on inference, HTTP and Runtime targets; redaction and interruption (`redactInput`, `redactOutput`, `interruptOutput`) are non-translatable                                                                                                                                                                                                                                                                                                                                                          | see `agentcore-targets-and-effects.md`, Guardrail scope                                                                                                                               |

## OAuth claims and principals

| Rule                                                                                                                                                                                                                                                                                      | Example                                                                     |
| ----------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- | --------------------------------------------------------------------------- |
| Every claim of the accepted token is an `OAuthUser` tag under its exact claim name. ID token (`allowedAudience`): `custom:<attr>`, `email`, `cognito:username`, `cognito:groups`, `sub`; access token (`allowedClients`): `username`, `scope`, `client_id`, `sub`, no custom attributes † | `principal.hasTag("custom:department")`                                     |
| `getTag` returns a String: a list claim is its JSON text, a number is a string. `.contains` on a tag is a type error; `getTags()` does not exist. To match one list element exactly, include its quotes                                                                                   | `principal.getTag("cognito:groups") like "*\"support\"*"`                   |
| `hasTag` before `getTag` on the same key is mandatory; an unguarded read is rejected at create, for every principal type in scope                                                                                                                                                         | `principal.hasTag("k") && principal.getTag("k") == "v"`                     |
| The `OAuthUser` entity id is the `sub` claim, not the user name or client id †                                                                                                                                                                                                            | `principal == AgentCore::OAuthUser::"<sub>"`                                |
| A guarded `forbid` lets a caller whose token lacks the claim through. For a restriction on a claim ("only callers with claim k = v"), write `forbid … unless { <guarded claim check> }` (the "only when" rule in [Before you write](#before-you-write)) †                                 | `forbid … unless { principal.hasTag("k") && principal.getTag("k") == "v" }` |
| IAM principals have no tags; a claim rule on an `AWS_IAM` Gateway cannot be expressed (a `hasTag` check on `IamEntity` validates but is never true) †                                                                                                                                     | —                                                                           |

- The developer confirms the claim names. On a `CUSTOM_JWT` Gateway, before you draft the first
  rule that reads a claim (`hasTag`/`getTag`), ask the developer to give or confirm the exact
  claim names, in one question for all rules. Suggest the names that the rule text or the
  `customClaims` in the authorizer configuration use, but treat them only as suggestions. Record
  the answer with `claims set --names <name> ...`; `validate` reports `claim_keys_not_confirmed`
  until you do, and `claim_key_unconfirmed` for a key outside the list. In document mode the
  document's `<idp_claims>` list is the confirmation (see `document-authoring.md`).
- Never read claim names from the identity provider (its discovery document, user pool, or
  directory), from a token, or from a setup label, and never add a provider-specific prefix.
  Ask for names only: never ask for a JWT, password, authorization code or credential file. A
  "no role" branch tests the same key: `!principal.hasTag("<key>")`.
- A successful sign-in and a passing validation do not prove that the invocation token carries
  the claim. Recommend testing an allowed, a denied and a no-claim identity.

## Names, limits and the policy set

| Rule                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                         | Example                       |
