# Auto-Labeling Plan

Keep `PLAN.md` current: each step's status (⬜ not started, 🔄 in progress, ✅ completed) and, under the step, the `id` of every `run-log.jsonl` entry it produced.

**Recommended for:** users who want a dataset labeled with an accuracy promise on the rows the jury auto-accepts, and more than the labels: people reviewing the rows the jury is unsure of and a random sample of the rows it accepted, a quality check or a transformation around the labeling, further passes that fold the corrections back in, or training on the labels afterwards. The plan also runs a run configuration the user hands in (a run-configuration file, also called a plan file). It does not train a model: to label and then train, run this plan first and hand its labeled dataset to the training plan at **Register and hand off**.

The labeling, review and transformation steps run in the `auto-labeling`, `human-in-the-loop`, `dataset-transformation` and `dataset-quality` references. This plan settles what each step decides and which run-configuration field it reads; those references say how to run it.

---

## Read This First

- **Gather everything once, before the plan.** **Gather the Run Configuration** settles every value the steps need. **Collect run parameters** records them, and later steps read them from that run-log entry. A value changes only with the user's explicit yes, recorded as a new entry.
- **A run configuration the user hands in replaces the questions.** Validate it (**Validating a Run Configuration**), ask only about the fields that are missing or invalid, and show the result with the plan for approval.
- **Three approvals come before the corpus is labeled:** the plan approval, the setup approval at **Confirm fields, task and spec** (the human labels and jobs of steps 4 to 6), and the hard stop at **Confirm and approve the run** (the refinement and corpus jobs of steps 8 to 10). The plan approval does not replace the later two. Each further pass needs its own yes.
- **The configuration answers the checkpoints of the other references that it settles.** Each takes its answer from the field's current value (**Run Log**):
  - The approvals at steps 3 and 7 stand in for the approval before a labeling run (`auto-labeling/references/full-loop.md`, HARD RULE #2 and the gate at Step 2; `auto-labeling/overview.md`, Principle 2). Step 3 covers the ceiling jobs of step 6, before the split sizes are known, and step 7, which shows them, covers the refinement and corpus jobs.
  - `review_low_confidence` and `review_high_confidence` answer the review offer of `auto-labeling/references/full-loop-review.md`, Step 7a.
  - `review_tool` answers the review-mode choice of `human-in-the-loop/overview.md`, Step 0b. The annotation questions of its Step 2 are still the user's to approve.
  - The plan approval confirms the DataSet names of the corpus and the seed: they are shown with the plan.
  - `cleanup.delete_scratch` replaces the cleanup question of the auto-labeling hand-off (**Cleanup Authorization**).
- **The spend limit is a stop.** With `spend_limit_usd` set, add each job's estimated model spend to the estimates of the jobs already run, before the job starts. When the sum would pass the limit, stop before the job and show both numbers. ⏸ The user raises the limit or ends the run.
- **The user starts every pass.** With `mode: manual_passes` the plan offers another pass after each one and never starts one by itself. When the user asks for rounds that run automatically, say that each pass is started by them and offer manual passes.

## Gather the Run Configuration

Before the first question, tell the user the labeling limits of `auto-labeling/overview.md` (Limits), among them the row cap: a job labels at most 50,000 rows. When the user hands in a run configuration, validate it (**Validating a Run Configuration**) instead of asking the questions below.

Otherwise ask three questions, and show the other fields the user is likely to change, with their defaults: `dataset_name` and the other names the run registers (**Run Configuration**, notes), `mode`, `refinement` and `max_refinements`, `jury`, `review_tool`, `consensus_metric`, `apply_corrections`, `spend_limit_usd` and `cleanup.delete_scratch`, with the fixed `confidence_level` and the `spot_check_size` the target gives. Every other field of **Run Configuration** keeps its default unless the user asks about it. The fields derived from the data (`task_type`, `text_fields`, `label_field`) are shown as coming from the data, to be confirmed at step 3, and `label_set` as taken from the guidelines or the label names; with labeled examples only, step 5 takes it from the label counts.

- **The shape question:** what do they have to describe the labels: written guidelines, labeled examples, both, or just the label names? The answer sets `spec_source` and `seed`:

  | Answer                | `spec_source` | `seed`               | What the plan adds                                                 |
  | --------------------- | ------------- | -------------------- | ------------------------------------------------------------------ |
  | Both                  | `guidelines`  | the labeled examples | nothing: the guidelines are the spec and the examples are the seed |
  | Labeled examples only | `induce`      | the labeled examples | rules induced from the seed's dev split at **Split and induce**    |
  | Guidelines only       | `guidelines`  | `none`               | **Build the seed**: people label a random sample of the corpus     |
  | Just the label names  | `cold_start`  | `none`               | **Build the seed**, then rules induced from it                     |

- **The target:** the accuracy the auto-accepted rows must meet (`accuracy_target`). Say with it that with three jurors only the rows all three agree on can be auto-accepted, and only when those rows are accurate enough to prove the target; otherwise every row goes to review. Say that the target is 0.85 to 0.99: a user who wants a lower one gets labels with no accuracy promise (`promise: none`), and the plan sends no target below 0.85. Say that the target may be out of reach, and that **Measure the ceiling** finds out before the paid labeling. A user who wants only the rows the model is "95% sure" about may mean a 0.95 target or the confidence level, which is already 95%: ask which. For `qa` on data that mixes answerable and unanswerable questions, say that the job certifies on one pooled exact-match rule and such a corpus rarely certifies (`auto-labeling/references/task-types.md`, Extractive QA), so offer a lower target or `promise: none` up front.
- **The review question:** whether people review the rows below the accept cutoff (`review_low_confidence`), and whether they check a random sample of the auto-accepted rows, the spot-check (`review_high_confidence`). Say with it that a review row that does not come back counts as wrong, that the spot-check sample is fixed before review starts and never redrawn, that without the spot-check the labels ship with no accuracy promise, and that with neither review one model labels the corpus, with no per-row confidence (the `Routing` note).

Then validate the run configuration (**Validating a Run Configuration**) and present the plan below with it (`planning/overview.md`, Phase 2). The plan approval also approves the run configuration and the names it shows.

## Steps

Steps 1 to 7 run once, and step 14 runs once at the end. Steps 8 to 13 are one pass. A further pass is a new project that enters at step 5 with the splits **Review Loop** lays out, then runs steps 8 to 13: append step 5 and steps 8 to 13 to `PLAN.md` again under a `Pass N` heading, and leave the steps of the earlier passes as they are.

1. **Collect run parameters**: Record the approved run configuration as the `collect-run-parameters` entry, with the path of the run-configuration file when the user handed one in. _(Reference: directory-management/overview.md, Run Log)_

2. **Read the first row and register**: Read the first row of the corpus, and of the seed when there is one, and register each that is not a DataSet yet, under the names shown with the plan. Register an `s3://` corpus with the `hub_ops` `import-s3` action (`auto-labeling/code_templates/hub_ops.py`), which reads nothing: the corpus is never read on the client. The run uploads a local corpus or seed as it is. From those rows come the field names, the proposed label and text fields, the task shape and a first estimate of the row count. _(Reference: auto-labeling/references/full-loop.md, Step 0)_

3. **Confirm fields, task and spec**: Show the label field, the text fields, the detected task type, the label set (with labeled examples only, step 5 supplies it) and where the spec comes from, and check them and the names against **Validating a Run Configuration**. With a seed, ask whether its rows were drawn from this corpus with the same `id` values, or labeled outside it, since the corpus run scores each test row against the corpus row with its `id`. A seed labeled outside the corpus can certify: the corpus run labels its test rows too, from their text fields, scores them and keeps them out of what ships, so give their share of the jury's calls in the corpus run's cost, and confirm that its `id` values are ones the corpus does not use (the job labels a test row whose `id` is a corpus row's but whose text is not, but a test row with another corpus row's `id` and no text field is scored against that row). The job fails when they and the corpus pass 50,000 rows, or, on a certifying run, when fewer than 50 test rows can be scored (corpus rows, or rows with every text field). The certificate is measured on the seed's mix of rows, so say so when the seed was drawn from another source. When the seed, or the sample of step 4, is too small for a test split of 50 rows, the run cannot be certified either: say so, and offer to have people label more random rows of the corpus into it first. Compare the row estimate with the row cap of `auto-labeling/overview.md` (Limits): a job labels at most 50,000 rows, so a bigger corpus runs as several plans (**Variations**). Give the cost of steps 4 to 6: on a cold start, the rows people label first and the sampling and overlay jobs; then the split job, the induction call when there is one, and the two ceiling jobs with the model id that runs them. ⏸ The user confirms the fields, answers those questions and approves that cost. Record the confirmed fields and the approval as the two `confirm-fields-task-and-spec` entries. For a handed-in file, ask only about a field the first rows contradict. _(Reference: auto-labeling/references/full-loop.md, Step 0.5)_

4. **Build the seed (cold start only)**: Skipped when `seed` is set, and in the opt-out (**Variations**). Otherwise people label a random sample of the corpus, and the labeled sample is the seed; the column that holds their labels is `label_field`. A label the model gave never counts as gold. Record the scratch entries this step registers (**Cleanup Authorization**). _(Reference: auto-labeling/references/cold-start.md; human-in-the-loop)_

5. **Split and induce**: Split the seed into dev, val and test, each a DataSet under its split name; a test split under 50 rows becomes a warning at the hard stop (**Validating a Run Configuration**), because the job then certifies nothing: it reports NotCertified (reason `insufficient_eval_rows`) and, with `Routing`, sends every row to review but the eval rows. An eval row that is a corpus row ships its gold, with `source` set to `human`, and is not routed; an eval row that is not a corpus row is labeled to be scored and does not ship. The 50 counts only the scored gold rows: those whose `id` matches a corpus row, and those with every text field the job labels to score them. The split reports the label counts (the `class_distribution` of a `dataset-transformation` `Split` job's manifest, or the dev split's own label counts for a local seed, which is client-readable), and the spec is written from the dev split. With labeled examples only (`spec_source: induce`), `label_set` is the set of labels in those counts: record it as the `split-and-induce` entry, and show it at the hard stop. Otherwise check `label_set` against those counts. Write the starting spec from `spec_source`, at most 64 KiB; with `induce`, or after a cold start, induce rules from dev. Draw the demos from dev: a sample of at most 100 rows and 64 KiB, written to S3 as `demos.jsonl` (`seed`, below). On a further pass, write the splits **Review Loop** lays out instead of splitting, freeze them, keep the last pass's spec and draw the demos from the new dev. _(Reference: auto-labeling/references/full-loop.md, Step 1; dataset-transformation; auto-labeling/references/spec-authoring.md; auto-labeling/references/spec-induction.md)_

6. **Measure the ceiling**: Two labeling jobs with the starting spec and the first `jury` model alone, one on dev and one on val, never on test. The val score is the ceiling. Say whether the target looks reachable and how many rows to expect in review. When it is out of reach, offer a lower target (0.85 at the least, the lowest the job takes) or labels with no accuracy promise (`promise: none`) at the next step. Record the scratch entries the two jobs register. _(Reference: auto-labeling/references/full-loop.md, Steps 2 and 3)_

7. **Confirm and approve the run**: Hard stop. Show the run configuration, the detected task, the starting spec, the split sizes, the measured ceiling, every model id and the cost line: the human labels first (the seed, the expected review rows and the spot-check), then the labeling jobs still to run and their estimated model spend (a corpus run without `Routing` runs one model, not the jury), against `spend_limit_usd` when it is set. Show any warning from **Validating a Run Configuration**, and with `cleanup.delete_scratch: true`, what it will delete and that the deletion cannot be undone. ⏸ The user approves the run. No refinement or corpus job runs before that. Record the approval as the `confirm-and-approve-the-run` entry. _(Reference: planning)_

8. **Label and refine**: Skipped when `refinement` is `off`, which overrides the refine-or-stop decision of `auto-labeling/references/refinement-routing.md`. Otherwise refine as `auto-labeling/references/spec-refinement.md` says, for at most `max_refinements` rounds. Each spec version runs as two labeling jobs with the first `jury` model alone, one on dev and one on val: dev's failure sample feeds the next edit, and val's score decides. The failure sample is the job's `labeling/failures.jsonl`: every row the job got wrong, with its full text, plus 2 right rows for each gold label, each with `predicted`, `gold`, `correct` and the reasoning. Show the user each edit before its round runs; the step 7 approval covers the rounds. Record the scratch entries each round registers. _(Reference: auto-labeling/references/full-loop.md, Steps 4 and 5; auto-labeling/references/spec-refinement.md)_

9. **Measure and certify**: One labeling job on the whole corpus with the frozen spec, the jury and `Routing`, test as the eval rows and, with `promise: exact`, `accuracy_target` as the target, registered as `dataset_name`; `summarization` sends no eval rows (`seed`, below), and a run with `promise: none` sends no `DatasetOptions.Config.Scoring.Target` (summarization still sends `DatasetOptions.Config.Scoring.Graders`) and, with `Routing`, routes on `review_bar` (the `Routing` note). The job labels every row, scores test once, sets the accept cutoff from the lower bound, and reports Certified, NotCertified or Partial (it stopped early and scored only the rows it labeled), with a one-line reason. A Certified result stays pending until the spot-check comes back at step 12. Plain labels run without `Routing` (the `Routing` note): one model labels every row, and the job scores test with no cutoff. _(Reference: auto-labeling/references/full-loop.md, Steps 6 and 7)_

10. **Route to review**: Skipped for plain labels, which run without `Routing` (the `Routing` note). Otherwise the same job writes the review DataSet (`review_dataset_name`): every row below the cutoff, marked `split: low_confidence`, and the spot-check rows it pins, marked `split: spot_check`. _(Reference: auto-labeling/references/full-loop-review.md, Step 7a)_

11. **Human review**: People review the rows the configuration sends them: the rows below the cutoff when `review_low_confidence` is on, the spot-check rows when `review_high_confidence` is on. With `review_high_confidence: false` and a seed, the job can still pin a spot-check (a no-target run routed on `review_bar`, the `Routing` note) and put it in the review DataSet; nobody is asked to check it, so the hand-off and the fold run with `--spot-check-off` (step 12). Reviewers label each row from its input fields alone, with the model's label hidden. With a `consensus_metric` other than `none`, each review task also asks for that score after the label, as one more annotation question (`human-in-the-loop/overview.md`, Step 2): a rating from 1 to 5 for `rating_1_5`, or the user's own question for `custom`. _(Reference: human-in-the-loop)_

12. **Apply corrections**: Human-in-the-loop returns only its export (the row's `id`, the label, completed / skipped) and stops: auto-labeling applies the corrections. The corpus run has already read the job's side file back into the project as `<project-dir>/review.model_output.jsonl`; the review rows stay in the review DataSet, which human-in-the-loop read by ARN. The fold (`fold_review.py hil --model-output`, the hand-off's `Contract.fold`) takes each review row's id and split from the side file and its label from the export, and writes `<project-dir>/review_seed.jsonl`. The side file stays in the job's `labeling/` folder, outside the review DataSet that `review/` registers, so reviewers label blind. With `review_high_confidence: false`, run the fold with `--spot-check-off` (the hand-off's `Contract.fold` carries it when `hil_handoff.py` got `--spot-check-off`): the job's `split: spot_check` rows then give no verdict, a row that did not come back is not a miss, and the returned ones fold as usual; the report says `spot_check_skipped`. Otherwise the fold scores the spot-check against the frozen labels, counting a row that did not come back or was marked unsure as a miss: the spot-check fails when the misses reach the withdraw threshold the job reports (`SpotCheckWithdrawAt`), and passes otherwise. What a failure means is the fold's basis, which it reads from `calib_accepted` on the job's answers: a Certified job writes it (true on the spot-check rows, false on the routed rows), and a job routed on `review_bar` writes none, but every review row it writes carries `_review_reason`, so the fold reports the basis as `bar` (it reports `unknown` only for a spot-check row with neither field). When a job's answers carry no `calib_accepted`, the job's `Status` agrees: on a Certified job a failure withdraws the certificate, and otherwise the auto-accepted rows missed the bar. When the share of the rows below the cutoff that came back is under `min_return_rate`, say so; the rows that did not come back keep the model's label and stay below the cutoff. Then write the overlay (the `seed_bootstrap` `overlay` action: the id and the person's label of each reviewed row, no input field), check it carries every reviewer label (`fold_review.py check --seed <project-dir>/review_seed.jsonl --labels <project-dir>/overlay.jsonl`), and apply the corrections as `apply_corrections` says (**Review Loop**). The labeled rows stay behind the API: nothing merges them on the client. _(Reference: auto-labeling/scripts/fold_review.py; dataset-transformation; auto-labeling/references/full-loop-review.md, Steps 7a and 7b)_

13. **Continue or finish**: Report what the pass bought: coverage (the share of rows auto-accepted), the certified bound, the corrections, the human labels used and the estimated spend. With `mode: manual_passes`, while the stop rule has not fired and fewer than `max_passes` passes have run, offer another pass in a new project with a fresh test split (**Review Loop**). Give its cost (the human labels of its fresh test split, review and spot-check, which count toward `human_label_budget`, and the estimated model spend of its jobs). When the corpus or `human_label_budget` cannot spare the fresh test split, say so and what the pass does without one (**Review Loop**). ⏸ It starts only on the user's yes, and enters at **Split and induce** (**Review Loop**). Record the `continue-or-finish` decision. _(Reference: planning)_

14. **Register and hand off**: The corpus run has already read the job's outputs back into the project, all but the labeled rows, which stay behind the API: `<project-dir>/labeled_dataset.json` (the deliverable: the labeled DataSet ARN, the review DataSet ARN and the S3 URI of the job's `output/labels.jsonl`), `<project-dir>/labeling_summary.json` (the job's `labeling/labeling_summary.json`) and `<project-dir>/held_out_report.json`, the job's `labeling/held_out_report.json` in the skill's shape (`primary`, `accuracy`, `counts` and the certificate fields, built from the job's summary and report). Write the run report with the auto-labeling skill's own report template (`auto-labeling/references/full-loop-delivery.md`, Step 8): `auto-labeling/code_templates/run_report.py` with `[PROJECT_DIR]` `<project-dir>` and `[DATASET]` `<dataset_name>` (no task setting: the job graded the task). With no local labels it builds the report from `labeled_dataset.json`, the job's summary (the review counts too) and the held-out report, with no per-row section; it shows the cutoff from `labeling_summary.json` (`AcceptThreshold`). When `AcceptThreshold` is null (reason `target_not_met` or `insufficient_eval_rows`), the job auto-accepted no row, and the hand-off says so. It writes `<project-dir>/report.html` and `<project-dir>/report.md`; the labeling job's own report, the one the labeled DataSet's entry leads to, stays where the job wrote it. The hand-off names the labeled DataSet ARN (after an `override`, the version the overlay job wrote) and gives, from `labeling_summary.json`, the held-out accuracy with its 95% lower bound (`HeldOutAccuracy`, `HeldOutLowerBound95`), the certified bound on the auto-accepted rows (`AcceptedHeldOutAccuracy`, `AcceptedLowerBound95`), coverage (`RowsAccepted / RowsLabeled`) and the review load (`RowsRouted` plus `SpotCheckRows`). After the fold of step 12, the report reads the fold's report (`<project-dir>/review_seed.fold.json`) and shows the spot-check agreement beside the certified bound, or that the spot-check withdrew the certificate; the hand-off states the same. With `promise: none`, the run report and the hand-off say that the labels carry no accuracy promise, whatever status the job reports. Apply **Cleanup Authorization** to the run's scratch entries, then offer the next steps of `auto-labeling/references/full-loop.md`, Step 11; training on the labels goes to a training plan (**Variations**, Label then train). _(Reference: auto-labeling/references/full-loop-delivery.md, Steps 8 and 8b; auto-labeling/references/full-loop.md, Step 11; auto-labeling/code_templates/run_report.py)_

## Run Configuration

Each field sets an option of the labeling job's request, stays with the plan (**Plan only**), or is a constant of the labeling job (**Fixed**). Request options are fields of the job's `GenerationConfig`, apart from `DatasetName` and `OutputDataConfig.OutputS3Uri`. Every labeling option sits under `DatasetOptions.Config` (`TextFields`, `Demos`, `EvaluationData`, `Scoring`, `Routing`), beside `DatasetOptions.Type`, and the notes and steps call them by those short names; the corpus comes in as `InputDataS3Uri` or `InputDatasetArn`, and a labeling request sets no `NumSamples`. The `auto-labeling` reference builds the request.

| `consensus_metric`       | `none`, `rating_1_5`, `custom`                                         | `none`                                                         | Plan only: the review tool records it                                                                   | A score reviewers give each label; it changes no label and no promise                                          |

| `min_return_rate`        | 0 to 1                                                                 | 0.98 of the rows below the cutoff; every spot-check row        | Plan only                                                                                               | The share of review rows that must come back                                                                   |
| `spend_limit_usd`        | a number above 0, or `none`                                            | `none`                                                         | Plan only: compared with an estimate (below)                                                            | The plan stops before a job whose estimated model spend would pass it                                          |
| `cleanup.delete_scratch` | `true` or `on`, `false` or `off`                                       | `false`                                                        | Plan only: authorizes `DeleteHubContent` on scratch entries                                             | What happens to the run's scratch entries (**Cleanup Authorization**)                                          |

Notes on the fields:

- **`seed`:** split into dev, val and test at step 5. Dev and val are the eval rows (`EvaluationData`) of the ceiling and refinement jobs, test is the corpus run's `EvaluationData`, and the demos come from dev: a sample of at most 100 rows and 64 KiB, written to S3 as `demos.jsonl`, and no demo is an eval row of the job it goes to, by `id` or by text, since the job fails before any model call when one is: the dev jobs score dev without the demo rows. `Demos` takes an `S3Uri` only. The corpus run scores each test row against the corpus row with its `id`, and labels a test row whose `id` is not a corpus id from its text fields to score it, so the seed's `id` values are this corpus's for the same rows, or values the corpus does not use. Overlay a seed's rows (`override`, Step 7b) only when they are corpus rows. A `summarization` job sends no `EvaluationData` at all: a seed, when there is one, supplies only `Demos` (`graders`, below).
- **`label_set`:** from the guidelines, or from the label names on a cold start. With labeled examples only, step 5 takes it from the split's label counts.
- **`spec_source`:** the request carries the finished spec, at most 64 KiB; induction runs before the job.
- **`dataset_name`, `review_dataset_name`:** 1 to 63 letters, digits and hyphens, starting and ending with a letter or digit, and so is every other name the run registers. The default of `dataset_name` is what the user calls the dataset (`<name>`) with `-labeled` added. The run also keeps the DataSets that steps 2 and 5 register: the corpus and the seed, under the names shown with the plan, and the dev, val and test splits, as `<dataset_name>-dev`, `<dataset_name>-val` and `<dataset_name>-test`. The other jobs register under run-unique names (**Cleanup Authorization**). The review DataSet is registered only by a corpus run that sets `Routing` (the `Routing` note).
- **`accuracy_target`:** the job takes 0.85 to 0.99, and only a corpus run with `promise: exact` sends it. A user who wants a lower target gets `promise: none`: the plan sends no target below 0.85.
- **`spot_check_size`:** the job sizes it from `DatasetOptions.Config.Scoring.Target` and reports it as `SpotCheckRows`; `auto-labeling/references/full-loop-review.md`, Step 7a, gives the size for each target. It is 19 at a 0.85 target, the lowest the job takes. The job pins a spot-check of that size with a target (`Scoring`), on a run that certified or a cold start (no eval rows). With eval rows and no target, a `classification`, `ner` or `qa` run routed on `review_bar` pins 29 rows, sized for a 0.90 target and withdrawn at 7 misses (the `Routing` note). It pins none on a run whose target did not certify, on a run with no eval rows and no target, and for `ordinal`, `llm_judge` and `summarization`.
- **`promise`:** `exact` is at least `accuracy_target` of the auto-accepted rows exactly right; `none` ships the labels with no promise. It is a run-configuration field, not one of the fields shown to the user. Whether the corpus run sets `Routing` follows from it and `review_low_confidence` (the `Routing` note).
- **`Routing`:** the one rule for whether a corpus run sets `Routing`. Every corpus run with `promise: exact` sets it, whatever `review_low_confidence` says: only with it does the job run the jury, give each row a confidence, set the cutoff and pin the spot-check. With `promise: none` the corpus run sets `Routing` only when `review_low_confidence` is on, since the rows below the cutoff need that confidence. Such a run sends no `DatasetOptions.Config.Scoring.Target` but sends test as `EvaluationData` when there is one, so the job routes on `review_bar`: a `classification`, `ner` or `qa` run reports NotCertified reason `no_target` and pins a spot-check of 29 rows sized for a 0.90 target, withdrawn at 7 misses, while an `ordinal` or `llm_judge` run reports NotCertified reason `task_not_certifiable` and pins none, since the job checks the task before the missing target. Either reports a held-out score that gates nothing, and no answer carries `calib_accepted`. Plain labels, `promise: none` with `review_low_confidence` off, run without it: one model labels every row, and the job scores test, when there is one, and samples its failures, with no cutoff and no review DataSet. A `summarization` run with `Routing` routes every summary to review, since its one model gives no confidence.
- **`jury`:** the default is the cross-provider jury of `auto-labeling/references/apply-and-confidence.md`, one model from each of three providers, with each id exactly as the synthetic data generation service accepts it; the plan names no model id of its own, and the hard stop shows the ids the run will use. A task that runs one model takes the first of them. How many models each task runs is a rule of **Validating a Run Configuration**. The ceiling and refinement jobs, and a corpus run without `Routing`, run the first model alone.
- **`graders`:** required for `summarization` in every case, with a seed or without: 1 to 3 model ids, none of them a `jury` model. They grade a sample of the summaries against their source text, never against gold. The request sends each grader as an object under `DatasetOptions.Config.Scoring.Graders`, `{"ModelId": "<id>"}` with optional `ReasoningEffort`, never as a bare id string (the service refuses `TargetTokensPerMinute`). No other task type uses them, `llm_judge` included, so it is `none` there.
- **`review_tool`:** the two review modes of `human-in-the-loop/overview.md` (Step 0b): `local` is local review, and `label_studio` is Label Studio (`review_mode: external_tool`).
- **`stop_rule`:** `target_met` once the promise is certified, `coverage_flat` once coverage stops rising, `human_label_budget` once the budget is spent. Only `manual_passes` reads it.
- **`spend_limit_usd`:** a limit on the agent's estimate, since the job reports no cost (**Read This First**).

## Validating a Run Configuration

Validate every run configuration before the user approves it, whether gathered from the questions or handed in, then the fields confirmed at step 3 and every later change.

A file is a `.md` file with one YAML block, a YAML file, or a JSON object, using the field names in **Run Configuration**. For the on-or-off fields (`refinement`, `review_low_confidence`, `review_high_confidence` and `cleanup.delete_scratch`), `on` and `true` mean the same, and so do `off` and `false`, quoted or not: YAML loads an unquoted `on` or `off` as true or false. Free-form guidelines, or a plan written for another tool, is not a run configuration: take the values it states and ask for the rest.

For each violation, name the field and what is wrong, and ask about those fields only.

1. **Required.** `corpus`. `label_field` when `seed` is set. `guidelines` when `spec_source` is `guidelines`. `label_set` for `classification` and `ner`, except with `spec_source: induce`, where step 5 takes it from the label counts. `graders` for `summarization`, with a seed or without. Every other field takes its default.
2. **Known fields.** A field that **Run Configuration** does not list is invalid: name the field, and the listed field it most likely means.
3. **Values and ranges.** Each value is one that the **Values** column of **Run Configuration** allows. A field set to its default is valid.
4. **Fixed fields.** `confidence_level`, `accept_cutoff`, `min_agreement`, `review_bar` and `spot_check_size` cannot be set. A value other than the fixed or computed one is invalid: say the field is fixed.
5. **Models.** Every `jury` and `graders` id is one the synthetic data generation service accepts, exactly as written (the service refuses any other at CreateJob and names the allowed list), and no id appears twice in either list. `graders` has 1 to 3 ids and does not include a `jury` model, which would grade its own summaries.
6. **Cross-field rules.**
   - `corpus` names one source: an `s3://` URI or a DataSet ARN.
   - `jury` has 2 to 5 models for `classification`, `ner` and `qa`, and exactly 1 for `ordinal`, `llm_judge` and `summarization`.
   - `graders` is `none` for every task type but `summarization`, `llm_judge` included.
   - `spec_source: induce` needs a `seed`. `spec_source: cold_start` needs `seed: none` and a `label_set`.
   - `review_high_confidence: false` needs `promise: none`, and its fold runs with `--spot-check-off` (step 12), since the job may still pin a spot-check. `promise: exact` needs `review_high_confidence: true`, an `accuracy_target` of 0.85 or more, and a task type that ships with an accuracy promise (not one of the next rule).
   - `ordinal`, `llm_judge` and `summarization` need `promise: none` and `review_high_confidence: false`: the labeling job certifies no floor for them, and their corpus run sends no `DatasetOptions.Config.Scoring.Target` (summarization still sends `DatasetOptions.Config.Scoring.Graders`), so the job pins no spot-check.
   - An `accuracy_target` below 0.85 is outside the range the job takes: say so, and offer `promise: none`, which sends no target.
   - `promise: none` with `review_low_confidence` off (plain labels, which set no `Routing`: the `Routing` note) needs `review_high_confidence: false`, since the job pins no spot-check.
   - `seed: none` runs **Build the seed** with `promise: exact`, and is the opt-out of **Variations** with `promise: none`.
   - `promise: none` with `review_high_confidence: true` needs a `seed` whose test rows the job can score (corpus rows, or rows with every `text_fields` column): with no target the job pins a spot-check only on a run that has eval rows (the `Routing` note).
   - `mode: single_pass` needs `max_passes: 1` and an `apply_corrections` other than `relabel`; `mode: manual_passes` needs `max_passes` of 2 or more.
   - `apply_corrections: relabel` needs `refinement: on`.
   - `stop_rule: human_label_budget` needs a `human_label_budget`.
   - A `consensus_metric` other than `none` needs `review_low_confidence` or `review_high_confidence` on.
   - `review_tool: label_studio` needs the Label Studio app in the user's space (`human-in-the-loop/overview.md`); without it, say so and offer `local`.
   - `label_field` is a column of the seed's first row and is not one of `text_fields`. Every `text_fields` name is a column of the corpus's first row and of the seed's.
   - With a `seed`, the first rows of the corpus and of the seed have an `id` field, and at step 3 the user confirms that the seed's `id` values are this corpus's for the same rows, or values the corpus does not use (a seed labeled outside the corpus).
   - At step 5, every label in the split's label counts is in `label_set`.
7. **Names.** `dataset_name`, `review_dataset_name` and the split names differ from one another, ignoring case, and from the names of the corpus's and the seed's DataSets, and every name the run registers follows the name rule in **Run Configuration**. At step 3, look up `dataset_name`, `review_dataset_name` and the split names in the hub of the corpus's DataSet (`aws sagemaker describe-hub-content --hub-name <hub> --hub-content-type DataSet --hub-content-name <name>`): a name that exists already would take the run's output as a new version, so it needs the user's explicit yes.
8. **Cleanup.** `cleanup.delete_scratch` is `true` or `false`. A missing or invalid value is `false`, which deletes nothing.
9. **Warnings.** These do not block the run; show them at **Confirm and approve the run**: a test split under 50 rows (step 5), counting only the scored gold rows (an `id` that matches a corpus row, or every text field so the job can label the row), which certifies nothing (NotCertified, reason `insufficient_eval_rows`) and sends every row to review but the eval rows, which ship their gold with `source` set to `human`; a `summarization` run with `review_low_confidence` on, which routes every summary to review (the `Routing` note); an `accuracy_target` of 0.95 or more with fewer than 100 test rows; a label in `label_set` with no rows in the split's label counts; `mode: manual_passes` with `refinement: off` (every further pass labels with the same spec); a `human_label_budget` below the human labels the plan already needs; and an estimated spend above `spend_limit_usd`.

## Cleanup Authorization

Scratch entries are the catalog entries that the run's working jobs register under run-unique names: the cold-start sample and its remainder, the two ceiling jobs, and the dev and val jobs of each refinement round. The labeled DataSet, the review DataSet, the dev, val and test DataSets, and the corpus and the seed are never scratch entries. Each scratch entry is one version of a DataSet, and a reused name adds a version to an existing entry, so cleanup works on versions, never on names. `DeleteHubContent` removes one version's catalog entry and leaves its files in S3; the entry cannot be restored.

When a job of steps 4, 6 or 8 completes, record each DataSet version it registered: an `artifact` entry with status `scratch`, with the versioned DataSet ARN as `arn` (for a labeling job, the job record's `DatasetArn`) and the job's ARN as `job_arn` (**Run Log**). These entries are the run's scratch entries, and nothing else is.

At **Register and hand off**, list the run's scratch entries with the run-log writer (`directory-management/overview.md`, Run Log): `python3 <skill-root>/references/directory-management/scripts/run_log.py list --project-dir <project-dir> --kind artifact --status scratch`. Then, by the current value of `cleanup.delete_scratch` (**Run Log**):

- **`false`:** delete nothing. The hand-off lists the entries, so the user can delete them later.
- **`true`:** delete every listed scratch entry. The user approved this at **Confirm and approve the run**, whose entry then has `approves_deletion: true`. When `cleanup.delete_scratch` became `true` after that approval, treat it as `false`: that approval did not show the deletion.

Delete a scratch entry with `aws sagemaker delete-hub-content --hub-name <hub> --hub-content-type DataSet --hub-content-name <name> --hub-content-version <version>`, taking the hub, the name and the version from its `arn`. Call it only for a version the step 7 approval covers, with `cleanup.delete_scratch: true` and `approves_deletion: true`. Nothing else authorizes a deletion, not a default and not an answer from an earlier run, and no approval covers another version of the same name or an entry that is not one of this run's scratch entries. A run that stops before **Register and hand off** deletes nothing. When a deletion is refused, for example because the role lacks `sagemaker:DeleteHubContent`, report it and keep the entries that remain. Record what was deleted and what was kept as the `register-and-hand-off` decision.

## Review Loop

`apply_corrections` decides what the people's corrections do:

- **`override`:** the corrections look like one-off judgment calls, scattered and with no shared pattern. A `dataset-transformation` overlay writes the people's labels over the model's by row id: one CodeGen job whose first input is a `hub_ops` `dt-view` of the labeled DataSet and second the overlay rows (`overlay.jsonl`, registered as a DataSet), with `overlay.handoff.json` as its spec; the `hub_ops` `promote` action adds its output as the labeled DataSet's next version (`auto-labeling/references/full-loop-review.md`, Step 7b). The spec does not change.
- **`relabel`:** the corrections show a rule gap: the same confusion repeating within a pair of labels, or one label swallowing another. Add the reviewed rows to dev and run another pass, whose **Label and refine** edits the spec from them. The refiner reads the rows' text, so download the review rows by the review DataSet ARN (seed-sized) and fold with `--sample` (`auto-labeling/references/cold-start.md`, Steady state).
- **`auto`:** pick one of the two from the pattern of corrections. The report says which ran and why. With `single_pass`, `auto` always overrides, and a rule gap it finds is reported as a reason to run manual passes.

Corrections feed the next pass like this:

- The corpus run sets `source` on every row: `jury` for `classification`, `ner` and `qa`, `resample:<model id>` for `ordinal` and `llm_judge`, and `human` for an eval row; without `Routing` it is the model id. A reviewed row is kept with `source` set to `human`; its `split`, `low_confidence` or `spot_check`, says which review it came from. Reviewed rows join the next pass's dev and its demos; val stays as it is, a random sample the refiner never saw (`auto-labeling/references/cold-start.md`, Steady state). The next pass's splits are laid out, not drawn again: dev is this pass's dev, its reviewed rows and its test rows; val is this pass's val; test is the fresh sample below. Write them (or, with no fresh test split, the layout in the last item) to the new project's `splits/` and run the `split_freeze` `freeze` action (`auto-labeling/code_templates/split_freeze.py`) there.
- Calibration and the promise rest only on human-labeled rows that nobody picked by confidence: the pass's test split while the rows come from the same source, and a new random sample that people label when they do not.
- Each pass scores its test split once, at **Measure and certify**. A further pass certifies only on a fresh test split: a uniform random sample, drawn when the user agrees to the pass, of the corpus rows no person has labeled yet (not in the seed or any split, review or spot-check), the size of the first test split and at least 50 rows. People label it before the pass's corpus run, and its rows ship with their human labels. The draw is a `dataset-transformation` CodeGen job over a `hub_ops` `dt-view` of the corpus and a DataSet of the ids people have labeled (the `hub_ops` `import-s3` action), told not to raise on unmatched ids; the `hub_ops` `register-output` action names the sample, and nothing lands as a version of the corpus. A project's frozen test rows never change, so each further pass is a new project and freeze, with the old test rows in its dev. Only the last pass's result can carry the promise: once a later pass scores its fresh test split, an earlier pass's promise no longer applies to what ships.
- When the corpus or `human_label_budget` cannot spare a fresh test split, the further pass may still run with `promise: none`: its test is this pass's test, its dev this pass's dev and reviewed rows, and it quotes no held-out number; the user may keep the earlier pass's certified output instead.

## Variations

- **Label only:** `review_low_confidence: false`, `review_high_confidence: false` and `promise: none`: plain labels, whose corpus run sets no `Routing` (the `Routing` note). Steps 10 and 11 are skipped and step 12 applies nothing. The labels come from one model, with no per-row confidence and no accuracy promise; report the test score as an estimate only.
- **No seed and no promise (the cold-start opt-out):** `seed: none`, `promise: none` and `review_high_confidence: false`, when the user will not have people label a sample (`auto-labeling/references/cold-start.md`). Steps 4 to 6 and 8 are skipped, and the spec runs as written. The job of step 9 has no eval rows and sends no `DatasetOptions.Config.Scoring.Target`. With `review_low_confidence` on it sets `Routing` (the `Routing` note), so its cutoff is `review_bar`, it reports NotCertified (reason `no_eval_data`), it pins no spot-check, and the rows below the cutoff go to review; with it off, the labels are plain.
- **Frozen spec:** `refinement: off`. **Label and refine** is skipped and the spec runs as written.
- **Cold start:** `seed: none`. **Build the seed** runs, and the run has no certified floor until the seed exists.
- **Several label columns:** one run configuration per column, each with its own `label_field`, `label_set`, `task_type`, `dataset_name` and `review_dataset_name`. Steps 3 to 13 run once per column; steps 1, 2 and 14 are shared, and step 14 offers the merged dataset of `auto-labeling/references/full-loop-delivery.md`, Step 8b.
- **Quality check first:** a `dataset-quality` evaluation of the corpus after step 2 registers it, and a `dataset-transformation` clean-up when it finds blank or duplicate rows. The clean-up runs on a `hub_ops` `dt-view` of the corpus, so its output does not become a version of the customer's corpus, and the `hub_ops` `register-output` action names the cleaned corpus; for `ExactDedup`, send `Normalize: false` (with `Normalize` the job failed live).
- **A corpus above the row limit:** `auto-labeling/overview.md` says how such a corpus is sampled down or split into parts. Each part is its own project, so it runs as its own plan, with its own names and its own accuracy promise.
- **Passes until the target is met:** `mode: manual_passes`. **Continue or finish** offers another pass until the stop rule fires.
- **Label then train:** this plan, then the training plan from **Register and hand off**.
